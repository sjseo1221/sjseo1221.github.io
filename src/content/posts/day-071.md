## 3. [과제] 채용공고 20개 분석 (Module 06 Homework)

> 단순 공고 스크랩이 아니라 직무 분석 → 반복 워딩 추출 → 경험 매칭 → Resume 재작성
> 최종 목표: "어떤 직무에 지원할 수 있나?"가 아니라 **"그 직무에서 요구하는 일을 증명할 수 있나?"**

### 과제 4단계

1. **20개**: 희망 직무 중심 원문 공고 수집
2. **반복 업무**: Responsibilities의 동사·업무 추출
3. **공통 기술**: Required·Tools의 기술 분류
4. **내 경험**: Evidence·Gap과 이력서 문장 연결

- 한 기업 JD를 베끼는 게 아니라, **같은 직무가 반복해서 요구하는 공통분모**를 찾는 것

### 어떤 공고를 모을까

- 권장 비중: 제1희망 직무 15개 내외 + 업무가 맞닿은 확장 직무 5개 내외
- 모두 동일 직무는 아닐 수 있으니 **라벨링**함. 신입·인턴·경력무관·주니어 공고 우선
- 예시(Agent 개발 희망): AI Agent Engineer 10 / LLM·AI App Engineer 5 / RAG·Python Backend 5. PM·데이터 분석을 무작정 섞지 않음
- 공고가 부족하면 과거 공고도 학습용으로 포함하되, 게시일·마감 여부·실제 지원 가능성을 구분함

- 공고 문장을 복사하는 게 아니라 **동일한 의미의 '내 실제 행동'을 선별**해 기술함

### 20개 공고로 이력서 상단 구조 바꾸기

- 분석 결과 예시(가상): 빈도 상위 Python·API·RAG·Evaluation / 공통 업무 도구 연결·성능 검증·오류 대응 / 공고별 차이 B2B 도메인·배포 수준·경력 / 상단 키워드는 검증된 기술만 반영
- 적용 순서: ① Target Position 명확화 → ② Summary에 직무 문제·강점 한 문장 → ③ Core Skills에 실제 경험 기술 배치 → ④ 해당 Evidence부터 Experience·Project 배열

### 실습: 대표 JD 1개 먼저 해부 (20개 모으기 전 품질 기준 맞추기)

STEP1 원문 보존(URL·조회일·회사·경력조건) → STEP2 직무 목적(누구의 어떤 문제를 해결하는 팀인지 1줄) → STEP3 업무 동사(Build/Operate/Evaluate/Improve) → STEP4 핵심 Skill(Required/Preferred/Tools 구분) → STEP5 나의 Evidence(실제 수행·프로젝트 결과·GAP 연결)

### 최종 제출물 — 표 하나가 아니라 분석 → 증명까지

- **A 공고 수집표**: 20건 링크/회사·직무, 경력·마감·업무 원문, Required·Preferred·Tools, 공고별 핵심 키워드
- **B 키워드 분석표**: 표준화된 Skill·Task, 20건 내 출현 공고 수, 필수·우대 출현 구분, 상위 공통역량 10개
- **C 내 경험 매칭표**: 키워드별 Evidence·GAP, 이력서 Bullet 수정 5개, 프로젝트 보완 계획 3개, 제1·확장 목표 직무
- 공개 가능한 내용만 기록하고 타인 개인정보·기업 내부 데이터는 공유하지 않음

**과제 공지**: 희망 직무 1개를 정하고 유사 업무의 국내 기업 공고 20건 수집 → 회사·직무·URL·조회일·경력·Responsibilities·Required·Preferred·Tools 정리 → 공통 키워드 상위 10개와 공고별 빈도 분석 → 내 경험·프로젝트에 매칭하고 GAP 표시 → 국문 이력서 Bullet 5개 + 보완 계획 3개

- **제출 구성: 엑셀 워크북 3개 탭 + 수정 Bullet 5개 + 1분 직무선택 이유 설명**

**FINAL CHECK** (수집 20건은 정답이 아니라 '반복 요구사항을 확인하는 표본')

- [ ] 20건을 같은 기준으로 비교했나
- [ ] 원문 URL·조회일·경력조건을 보존했나
- [ ] Responsibilities에서 실제 업무 동사를 뽑았나
- [ ] Required와 Preferred를 나눴나
- [ ] 상위 10개 키워드의 출현 공고 수를 셌나
- [ ] 없는 경험은 GAP으로 남겼나
- [ ] 확인 가능한 개인 기여·수치로 Bullet 5개를 썼나

### 강사가 보여준 실제 예시

- **엑셀 '보완사항' 탭**: 미비역량 항목(ML/DL, DB·데이터핸들링, 활용 Data Scope, 분석 노하우/Tool)별로 내용 → 관련 공고 수(모수 24건, `=COUNTA()`로 집계, 막대로 시각화) → 관련 공고번호 → 간접경험 여부(직장 내 / 교내·연구, Y/N) 정리. 예: "기존 BA 내 ML 경험 부족"은 거의 모든 공고에서 요구, "데이터셋 경험 한계"는 모든 공고 공통사항
- **이력서 피드백 메모 (노란 형광)**
  - 수집했던 JD 내용들이 최대한 많이 포함되어야 함
  - 정리만 하지 말고 **무슨 일을 어떻게 얼마나 잘해서 어떤 결과가 나왔는지** 보여줄 것
  - 타겟 공고가 있다면 JD 문장을 하나씩 가져와 그 관련 내용을 상세하게 정리
  - 상세히 쓴다 = 뭘 어떻게 했고, 어느 정도 볼륨으로, 어떤 방식으로 했는지, 본인이 뭘 잘했고 어떻게 해서 어떤 성과를 만들었는지까지 작성

## 4. Capstone 경험을 채용 Evidence로 만들기 (Module 03)

> 프로젝트 이름 하나 적고 끝내지 말고 **역할·규모·행동·결과**를 확보함

### 경험은 4곳에서 확보 가능

| Career | Education | Project | Activity |
|---|---|---|---|
| 경력·인턴·아르바이트: 업무 개선, 데이터 처리, 고객 응대 | 전공·연구·수업: 분석, 프로그래밍, 문제 해결 | Capstone·개인 개발: 기능 구현, 평가, 배포, 협업 | 동아리·대외활동: 일정, 조율, 리서치, 성과 관리 |

- 단, 학교·모의 프로젝트를 기업 실무 경력으로 바꿔 쓰면 안 됨

### Evidence의 5단계 — 교육 수료와 실제 성과를 같은 무게로 쓰지 않음

```
LEVEL 1 KNOWLEDGE       교육 수강·기술 이해
LEVEL 2 IMPLEMENTATION  작동하는 기능 구현
LEVEL 3 VALIDATION      테스트·품질 평가
LEVEL 4 IMPROVEMENT     변경 전후 성능 개선
LEVEL 5 BUSINESS IMPACT 현업 시간·비용·오류 개선
```

- 상위 단계가 없는 신입은 **Level 3~4 검증 증거라도 확보하는 것이 실질적인 차별화**

### 경험 문장의 기본 구조: Task + Scope + Action + Result

| TASK 무엇을 위해 | SCOPE 어느 정도 규모로 | ACTION 내가 어떻게 | RESULT 무엇이 달라졌나 |
|---|---|---|---|
| 사용자 문의 자동화 | 문서 240건 / 팀 4명 | Chunking·Search 평가 | 검증된 전후 개선 수치 |

- 결과 수치가 없으면 직접 관찰한 기능·산출물·테스트 결과를 사실대로 제시

### STAR는 서술형 스토리, 이력서는 압축된 Evidence

- **면접 답변(STAR)**: S 문서 검색 결과가 불안정한 문제 → T 관련 문서를 근거로 답하도록 개선 필요 → A 질의셋 생성·청킹 비교·검색 실패 분석 → R 검증 결과와 개선 수치 설명
- **이력서 Bullet(TSAR)**: 문서 기반 RAG 검색 품질 개선 프로젝트 / 평가 질문셋 구성 및 Chunking 전략별 검색 성능 비교 / 오류 유형 분석 기반 Retrieval Pipeline 개선 / 검증 결과 기반 최종 설계안 문서화

### 수치화는 매출만이 아님

| 규모 | 정확도 | 시간 |
|---|---|---|
| 문서 수 / 질의 수 / 사용자 수 | 정답률 / 검색 적중 / 오류 | p95 응답시간 / 처리시간 |
| **비용** | **안정성** | **활용성** |
| 토큰 비용 / API 호출 비용 | 작업 성공률 / 재시도율 | 완료율 / 피드백 / 만족도 |

### AI Agent 성과지표 — 정의를 알고 써야 함 ⭐

| 지표 | 정의 |
|---|---|
| **Hit@k** | 정답 근거를 상위 k개 검색결과에 포함한 질의 비율 |
| **Task Success Rate** | 정의한 성공 조건을 만족한 실행 비율 |
| **Faithfulness** | 답변 주장이 제공된 근거에 부합하는지 평가 |
| **p95 Latency** | 응답시간 분포에서 95백분위 지연시간 |
| **Cost / Request** | 요청 1건당 API·모델 사용비용 |
| **Regression Pass** | 변경 이후 기존 테스트를 통과한 비율 |

### 한 개 Capstone에서도 여러 직무의 Evidence를 만들 수 있음

01 기획·요구사항(Problem/PRD) → 02 데이터·RAG(Data/Retrieval) → 03 Agent·API(Tool/Backend) → 04 UI·연동(Frontend/Demo) → 05 평가·운영(QA/Monitoring)

- 한 명이 모두 했다고 쓰지 말고 **본인이 맡은 모듈·의사결정·결과를 정확히 분리**

### Capstone 8주 — 끝나고 기억을 더듬지 말고 작업 중 Evidence 수집

| W1 | W2 | W3-4 | W5 | W6 | W7 | W8 |
|---|---|---|---|---|---|---|
| 요구사항: 문제 정의·역할 분담 | 기준선: 데이터셋·Baseline | 개발: Repo·API·Agent Trace | 검증: 평가셋·예외 테스트 | 개선: Before/After 비교 | 배포: Demo·운영·에러 로그 | 정리: README·Resume Bullet |

### "AI 챗봇 개발"을 JD에 맞는 경험으로 바꾸기

- BEFORE: "AI 챗봇 프로젝트 참여" → 업무·규모·내 역할·사용 기술·검증 결과가 안 보여서 약함
- AFTER: "사내 문서 QA용 RAG 기능 설계·구현 / 질문 평가셋 구성 및 검색 실패 사례 분류 / Chunking 전략별 Retrieval 결과 비교 / [측정된 개선 결과가 있다면 수치 기입]"
- 정보량과 증거를 늘리는 작업이지 어려운 단어로 치장하는 게 아님. 수행하지 않은 테스트·개선은 반드시 삭제

### 문과·경력전환자 — 이전 경험이 기술의 활용 맥락

| 기존 경험 | 업무 문제 | AI Capstone 연결 |
|---|---|---|
| HR·교육운영 | 온보딩·FAQ 반복 문의 | HR Knowledge Agent / 교육효과 지표 |
| 금융·회계 | 증빙·규정 대조 반복 | 문서 검증 Agent / 오류·시간 |
| 마케팅·콘텐츠 | VOC 분류와 응대 | VOC Agent / 처리시간·정확도 |
| SCM·운영 | 납기·재고 정보 조회 | 업무지원 Agent / 정보 추적 |
| 행정·고객지원 | 정책·매뉴얼 검색 | RAG FAQ / 근거·응답 품질 |

- **도메인 문제 + AI 설계·활용 경험**을 함께 제시

### 경험에서 정보를 끌어내는 질문 8가지

01 왜 이 문제가 중요했나 / 02 내가 맡은 모듈·의사결정은 / 03 기존 방식은 왜 안 됐나 / 04 어떤 기술 대안을 비교했나 / 05 데이터·문서·요청 규모는 / 06 어떤 오류를 직접 발견·수정했나 / 07 개선 전후 수치를 직접 측정했나 / 08 Repo·문서·로그 중 남은 증거는

- 이 질문에 답하면 자기소개서 소재가 아니라 **이력서 근거**가 됨

### WORKSHOP 02 — 프로젝트 한 개를 Evidence로 (개별 15분 + 그룹 코멘트 5분)

TASK 누구의 어떤 문제? / SCOPE 데이터·사용자·기능 규모? / ACTION 본인이 직접 설계·개발한 것? / RESULT 실제 확인된 변화·검증? / PROOF Repo·테스트·데모 링크?

- 수치를 모르면 빈칸에 **"미측정"**을 쓰고 재현 가능한 측정 계획을 세움

## 5. 합격 사례로 보는 이력서 문장 (Module 05)

> 업무를 설명하는 문장에서 → 채용 기준을 증명하는 문장으로

### 이력서는 자기소개가 아니라 '실제 수행한 업무의 증거'

채용담당자가 Bullet 한 줄에서 확인하려는 4가지:

| 무엇을 맡았나 | 어느 정도 했나 | 내가 어떻게 했나 | 그래서 무엇이 달라졌나 |
|---|---|---|---|
| JD 업무명과 연결되는 Task (예: AI 모델 품질 평가) | 대상·기간·규모·건수 (예: 월 100건 이상 운영 요청) | 직접 수행한 Action과 Tool (예: SQL 기반 이상치 조사) | 변화·성과·검증 결과 (예: 5명 5시간 → 1명 1시간) |

- **업무명 + 도구만 쓰면 기술 목록, 담당 범위와 검증 결과를 붙이면 채용 증거**

### 한 문장 공식 예시 (LINE DataOps 사례)

- TASK AI 데이터 품질 검증 / SCOPE 영상·이미지, 실내외 조건 / ACTION Blur 지표·전처리 로직 설계 / RESULT 품질 기준·실패 유형 정리
- 완성: "얼굴 위조 탐지 모델 학습용 이미지·영상 데이터 품질 검증을 위해 Laplacian Variance 기반 Blur 지표 설계 및 OpenCV·DeepFace 전처리 자동화"
- 수치가 없으면 임의의 정확도 향상률을 넣지 않음. 확인 가능한 방법·산출물·검증 범위를 적음

### 약한 문장을 강하게 만드는 5단계 (Evidence Ladder)

```
1 업무명     AI 데이터 처리
2 직무 맥락  AI 모델 학습용 데이터 전처리
3 본인 행동  OpenCV 기반 얼굴 검출·Crop 자동화
4 범위와 판단 실내외·조명·각도 조건별 데이터 품질 검증
5 검증 근거  Blur 지표·품질 기준·실패 패턴·보완 과제 문서화
```

### 좋은 숫자와 위험한 숫자

- **사용해도 되는 수치**: 실제 문서·로그·테스트로 확인 가능 / 분모와 단위가 명확 / 본인 기여 범위와 결과 구분 / 평가 지표 의미를 설명 가능
- **다시 확인할 수치**: 정확도 100%(테스트 몇 건인지 불명확) / 처리시간 90% 감소(전후 기준 불일치) / 팀 성과를 개인 성과로 기재 / AUC·mAP·Accuracy를 같은 지표처럼 표현
- 검증 질문: **언제·몇 건·어떤 환경에서·어떤 기준으로 측정한 숫자인가?**

### [합격 사례 A] EY한영 — 코드 작성보다 업무 변화가 핵심

- 자동화 BEFORE: "Selenium을 활용한 업무 자동화 / 대시보드 설정 관리"
- AFTER: "Brandwatch 대시보드 내 50개 이상 위젯 설정 변경 업무 자동화를 위한 Selenium 스크립트 개발 / 기존 5명·5시간 이상 소요 작업을 1명·1시간 이내 처리하도록 개선"
  - 업무 대상(50+ 위젯) → 행동(Selenium 자동화) → 전후 변화(인원·시간)를 한 번에 보여줌
- 면접용 풀이: 문제(50개+ 위젯 반복 수작업) → 분석(브라우저 경로·설정 변경 패턴 비교) → 행동(자동화 코드 작성·유지) → 결과(5명·5시간 → 1명·1시간)
  - 예상 후속 질문: 어떤 클릭·페이지 이동을 자동화했나? / 오류 나면 어떻게 복구했나? / 성과는 어떤 조건에서 측정했나?
- API·ETL BEFORE: "데이터 분석 및 리포트 작성 / API 업무 수행" → AFTER: "Sprinklr API Request 로직 검토 및 중복 요청 단일화 기반 데이터 추출 자동화, 추출시간 80% 이상 단축 / Python 기반 Buzz Volume·Sentiment 데이터 ETL 로직 자동화"
  - **같은 경험도 타깃 JD에 따라 다르게**: Data Pipeline JD면 API·ETL·Python을, 업무 개선 JD면 중복 요청 제거·처리시간 단축을 앞에 배치. 다른 프로젝트 성과를 합쳐 쓰지 않음

### [합격 사례 B] 교육 프로젝트도 정확히 쓰면 경쟁력

- BEFORE: "딥러닝 모델 학습 프로젝트 / AI 서비스 API 개발"
- AFTER: "이미지 4,200장·3개 클래스 YOLOv5 학습 데이터 구축 및 mAP@0.5 88.1% 기록 / FastAPI 기반 이미지 추론 API 구현, 테스트 평균 응답시간 1.8초·정상 응답률 100% 기록"
- 데이터 규모 → 모델·지표 → 서빙(API) → 실측 응답 결과까지, JD의 ML+Backend 문맥에 연결. 교육/프로젝트 섹션에 작성하고 기업경력과 구분함
- **높은 Accuracy 하나로 "좋은 모델"이라 할 수 없음** ⭐
  - Neural Network Accuracy 97.87% → 불균형 데이터에서 다수 클래스 편향
  - Random Forest + ROSE, Accuracy 68.35%·AUC 0.73 → 실제 부상 구분 성능과 편향을 함께 고려한 선택
  - 문장 방향: 여러 모델의 Accuracy·AUC·데이터 불균형 문제를 비교한 뒤 모델 선택 근거 제시

### [합격 사례 C] Apple — "데이터 검수"를 직무 언어로

- BEFORE: "AI 모델 데이터 검수 / 사용자 피드백 관리"
- AFTER: "다국어·멀티플랫폼 AI 모델 응답의 정확성·사실성·현지화 품질 평가 및 이상 사례 식별 / 가이드라인 기반 개별 사례 판단, 모호한 사례의 QA 이력·유사 사례 검토 및 Escalation / 모델 업데이트 후 회귀 테스트·평가 근거 문서화"
- LLM Evaluation JD에서는 **정확성·일관성·회귀 테스트·판단 근거**가 직접 연결되는 언어
- IT 리스크 BEFORE: "IT 감사 업무 수행 / 보안 규정 확인" → AFTER: "K-SOX 기반 ITGC·ITAC 통제 검토 및 시스템 운영자 인터뷰·감사 증빙 분석을 통한 주요 IT 리스크 식별 / 접근·변경·운영 통제의 미비점 조사 및 보완 절차·통제 설계 지원"
  - IT Risk JD엔 K-SOX·ITGC·Evidence Review를, AI Governance JD엔 판단 기준·통제·위험 분석을 우선 강조. 문서에 없는 경험(모델 보안 연구, Red Team, K8s 운영 등)은 추가하지 않음

### 같은 사람도 지원 직무에 따라 "상단의 경험"이 달라짐

| 목표 직무 | 1순위 전면 배치 경험 | 확인해야 할 부족 요소 |
|---|---|---|
| AI Data Quality / Evaluation | 이미지·영상 품질 기준, 실패 패턴 분석 | 실제 데이터 규모·평가 기준·오류 개선 |
| ML / CV Engineer | YOLOv5 학습, mAP@0.5, 성능 비교 | 모델 학습 설계·재현성·배포 경험 |
| Python Backend / AI App | FastAPI 추론 API, 응답시간 테스트 | DB·인증·테스트·배포 스택 |
| IT Operations / SRE 보조 | 월 100건+ 이슈 대응, SQL 진단 | Linux·Cloud·CI/CD 실무 |
| IT Risk / Governance | ITGC·ITAC·통제 증빙·판단 기록 | 목표 산업 규정·AI 정책 지식 |

- 주의: 동일한 실적을 반복 배치하거나 수행하지 않은 업무로 바꾸는 것은 정합성이 아니라 **과장**

### 경력기술서는 '업무 단계' 기준으로 카테고리를 묶음

| Data / AI 품질 | 서비스·개발 | IT 운영·리스크 |
|---|---|---|
| ① 데이터 수집·설계 ② 전처리·검증 자동화 ③ 모델 실패·오류 분석 ④ 품질기준·가이드 개선 | ① 요구사항·아키텍처 ② 구현·API·DB 연동 ③ 테스트·평가 ④ 배포·운영·개선 | ① 시스템·업무 범위 ② 모니터링·증빙 검토 ③ 이슈 분석·개선 ④ 표준화·조율·성과 |

- 강의 원칙: **한 Bullet = 한 가지 메시지 / 업무 세부 범위를 명사형 / 성과·수치는 확인 후 추가**

### Capstone은 팀 결과와 "내가 만든 것"을 분리

| 확보할 증거 | 예시 질문 | 기록 형태 |
|---|---|---|
| 담당 기능 | RAG, API, UI, Eval 중 무엇을 직접 했나 | 모듈명, PR·Commit 링크 |
| 기준과 비교 | 개선 이전 Baseline과 평가셋이 있었나 | 테스트 결과표, 조건 |
| 문제 해결 | 검색 오류·Tool 실패를 어떻게 진단했나 | 이슈·재현·수정 로그 |
| 운영 결과 | 정확도·Latency·비용을 어떻게 측정했나 | 지표 단위·기간·스크린샷 |
| 팀 기여 | 팀 최종 결과 중 개인 기여는 | 담당 범위·리뷰 이력 |

- 명확한 기준: 문제 → 판단 → 본인 행동 → 결과 / 수치가 없다면 테스트·코드·산출물 등 검증 근거

## 6. ATS와 사람 모두 읽기 쉬운 Resume (Module 04)

> 기술을 나열하는 문서가 아니라 JD별로 수행 가능성을 증명하는 구조

### AI Agent 주니어 이력서 기본 구조

HEADER(이름·연락처·LinkedIn·GitHub) → SUMMARY(어떤 영역의 일을 해왔나) → TECH SKILLS(업무에 실제 사용한 언어·도구) → PROJECTS(직무 관련 프로젝트·역할·성과) → EXPERIENCE(경력·인턴·전공·관련 활동) → EDUCATION(학력·관련 교육·자격)

- 프로젝트와 경력의 순서는 **근거 강도에 따라 조정**, 공고에서 요구한 문서 형식을 우선

### ATS는 채용 절차를 관리하는 시스템

01 지원서·파일 접수 → 02 문서 정보 추출(파일 구조에 따라 Parsing) → 03 요건·Skill 대조(도입 기능·회사 설정에 따라 다름) → 04 채용담당자 검토(경력·역할·성과의 설득력 판단)

- 자동 점수 하나로 합격·탈락이 결정된다고 단정하지 않음. Workday에 Skill Match 기능이 있지만 모든 기업에 동일하게 적용되진 않음

### ATS-friendly = 잘 읽히는 구조 + 사실에 맞는 키워드

| DO (권장) | AVOID (주의) |
|---|---|
| 표준 제목: Experience, Projects, Skills | 텍스트 대신 이미지로 만든 이력서 |
| 회사·역할·기간을 명확히 구분 | 복잡한 표·다단·텍스트박스 남용 |
| 실제 사용한 스킬을 문맥 속에 사용 | 실제로 안 한 기술명 반복 삽입 |
| 제출 후 추출된 정보 반드시 확인 | 자체 ATS 점수를 실제 기업 기준으로 오해 |

### 상단 Summary와 Core Skills는 역할이 다름

- **Professional Summary**: 어떤 직무 영역을 지향하고, 무슨 프로젝트·산출물을 만들었고, 어떤 문제를 해결했는지 3~4줄 (자기 성격이 아니라 채용 직무의 언어로)
- **Core Technical Skills**: Languages(Python, SQL) / AI·LLM(LangGraph, RAG) / Backend(FastAPI, REST API) / Workflow(Git, Docker, Testing)
- 실습하지 않은 LangGraph·Docker 등은 빼야 하며, **사용 깊이도 면접에서 설명 가능**해야 함

### 경험 Bullet 하나에도 JD 관련성과 증명이 모두 필요

> "사내 문서 240건 기반 RAG 검색 기능 구현 및 평가 질문 30개 구성, **Chunking 전략별 검색 성능 비교 및 오류 유형 분석**"

- Scope: 문서 240건·질문 30개 / Action: RAG·Chunking·Evaluation / Evidence: 성능 비교·오류 분석
- 명사형 국문 Bullet → 행동 중심 영문 Bullet. 위 문장은 구조 설명용 가상 사례이며 수치는 실측한 경우에만 사용

### 한 페이지 이력서 예시 (가상)

```
홍길동 | AI Agent Engineer
SUMMARY    Python·LLM·RAG 기반 AI 서비스 프로젝트 참여, 평가·오류 분석 경험
SKILLS     Python · FastAPI · LangChain · RAG · Git (실제 사용 기술만 기재)
PROJECT    AI 문서검색 Agent | 역할: Retrieval 파이프라인·평가
           • 데이터 정제 및 검색 흐름 구현
           • 평가 질문셋 구성과 오류 유형 분류
EXPERIENCE 이전 직무 관련 경험 중 해당 직무와 연결되는 활동
EDUCATION  관련 교육 · 학위 · 실습 과정
```

### GitHub README도 JD 중심의 Evidence 문서

코드를 열어보지 않아도 문제·역할·검증 방법을 이해하도록 설계함

01 Problem & User(누구의 어떤 문제) · 02 Role & Scope(내 기여·기간·팀 역할) · 03 Architecture(데이터·Agent·API 흐름도) · 04 Evaluation(평가 질문셋·Baseline·결과) · 05 Failures & Fix(한계·원인·수정 이력) · 06 Demo & Run(실행법·데모·재현 조건)

### 이력서 신뢰를 떨어뜨리는 실수 5가지

| 실수 | 약한 표현 | 개선 방향 |
|---|---|---|
| 기술 나열 | LangGraph·RAG·FastAPI를 배웠다 | 기능 구현 위치·담당 역할·평가 근거 |
| 팀 성과 독점 | 팀 프로젝트 전체를 내가 개발 | 본인 모듈·개인 결정·PR 링크 |
| 성과 수치 조작 | 근거 없는 "정확도 95%" | 평가 조건·분모·측정 결과 |
| 과도한 키워드 | JD 용어를 무리하게 반복 | 진짜 경험 문장 안에서 자연스럽게 |
| 경력 과장 | 교육 PoC를 실제 서비스 운영처럼 | 교육 프로젝트와 기업 실무 구분 |

- 기술 명칭이 많을수록 좋은 이력서가 되는 게 아님

### WORKSHOP 03 — 내 이력서 문장 3개 완성 (개별 20분 + 피어 리뷰 5분)
