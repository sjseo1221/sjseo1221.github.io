## 핵심 개념

### Nemotron: NVIDIA의 오픈 모델

장기 실행 에이전트 시스템에는 여러 모델이 협업하는 구조가 필요하며, 추론 때 연산을 더 쓸수록 성능이 오르는 Test-time scaling(Long thinking)도 중요해짐. NVIDIA는 Hugging Face 기준 오픈소스 AI 저장소 성장 1위라고 강조했고, Cosmos(피지컬 AI)·GR00T(로보틱스)·Alpamayo(자율주행) 같은 오픈 모델도 함께 소개함.

세대별 흐름은 다음과 같음.

- Nemotron 1: Llama 기반에 추론 능력을 추가함.
- Nemotron 2: 하이브리드 아키텍처로 추론 효율을 개선함.
- Nemotron 3: 멀티 에이전트용 하이브리드 MoE로 구성함.
- Nemotron 4: 3과 차이가 크고, 다양한 형태를 하나의 모델로 다루는 방향이라고 들음(메모).

### Nemotron 3 Ultra 학습 5단계

모델은 550B-A55B Latent MoE이며, 하이브리드 Mamba-Attention 구조를 사용함.

1. 사전학습: 약 20T 토큰, NVFP4 정밀도로 학습함.
2. SFT: DeepSeek·GPT-OSS·Qwen·MiniMax·GLM 등 교사 모델 데이터와 NeMo Data Designer 합성 데이터를 합쳐 약 50M 샘플을 사용함.
3. RL: 검증 가능한 보상(RLVR)을 사용하고, NeMo Gym의 통합 환경 15개(터미널, SWE, 검색, 도구 사용, 수학, 코드 등)에서 학습함.
4. MOPD: 도메인 특화 교사 모델 10개 이상으로 멀티 교사 증류를 진행함.
5. MTP 부스팅 + 양자화: Multi-Token Prediction과 선택적 PTQ(ModelOpt)로 긴 컨텍스트 추론을 효율화함.

### MoE와 Latent MoE

MoE는 적은 활성 파라미터로 같은 수준의 성능을 냄. Latent MoE는 낮은 차원으로 압축한 상태에서 전문가 연산을 한 뒤 다시 높은 차원으로 복원함. 이 방식은 전문가 연산량을 줄이고, 분산 환경의 통신 병목도 줄임. 네 가지 측면에서 추론이 최적화된다고 했으나 항목은 기록하지 못함.

### VLM 구조

1. 비전 인코더: 자체 ViT를 처음부터 학습함. Conv3d 패치로 이미지와 영상을 모두 처리하고, Window 어텐션과 Full 어텐션을 섞어 8K 이상의 입력을 처리함.
2. 어댑터: 패치 특징을 LLM 임베딩 공간의 토큰으로 투영함.
3. LLM: Nemotron 3 Nano 스타일의 30B-A3B MoE를 사용함. 비전 토큰을 텍스트와 섞어 입력하고, 손실은 텍스트 토큰에만 계산함.

비전 인코더가 전체 연산에서 큰 비중을 차지할 수 있다는 점도 메모함.

### VLM 학습 파이프라인

시작점은 LLM 백본(Text-SFT 모델 또는 베이스 LLM)임.

- Part 1. MMPT(멀티모달 사전학습): Megatron Bridge로 400B 토큰을 학습함.
- Part 2. 멀티모달 SFT(컨텍스트 길이별 단계 학습) 후 멀티모달 RL(RLVR)을 진행함.
- Part 3. OmniEvaluator: 전 단계에 걸친 통합 평가 시스템임. 모든 벤치마크를 한곳에서 실행하고, 추론 백엔드에 무관하며, 검증기와 few-shot을 지원하고, 모든 결과의 출처(provenance)를 기록함. 평가 결과는 데이터 믹스와 학습 레시피에 다시 반영됨.

최종 목표는 옴니모달임.

### 비전을 붙이면 학습이 불안정해짐

- 2024년 이전 NeMo 시절에는 LLM 레시피가 잘 돌았지만, 비전을 붙이자 학습이 계속 중단되어 수동 재시작을 반복함(약 4,697 스텝까지 여러 번 재시작).
- 디버깅은 대부분 직접 수행했고, 코딩 에이전트로 문제를 재현한 뒤 이분 탐색(bisect)으로 원인을 좁힘.
- 현재 Megatron Bridge에서는 2T+ 토큰 풀을 멀티노드 B200에서 장시간 안정적으로 학습함.
- 찾아서 업스트림한 이슈는 packed sequence의 CP gradient 문제, 0-image-rank hang(이미지 없는 랭크에서 멈춤), tied-embedding 체크포인트 문제임.
- 이미지 토큰 불균형(image token imbalance)이 학습 속도와 비용에 영향을 줌.

### MoE 추론 최적화 단계

슬라이드 상단 탭 기준 순서는 Baseline → +Kernels → +Host → +Comm → Serving layer(+naive → +Routing → +P/D)임.

### Decode MoE: Expert GEMM 주변 작업의 융합

조건은 MoE 레이어 94개, 요청당 127 스텝 생성, 전문가 128개 중 8개 선택임.

디코드 MoE는 메모리 병목(memory-bound)임. 토큰 1개·레이어 1개당 NVFP4 가중치 약 85MB를 읽는데 연산은 약 0.3 GFLOP뿐이라, Roofline 기준 4 FLOP/byte 미만이며 HBM 대역폭(8 TB/s)이 성능을 결정함.

따라서 해결책은 연산을 빠르게 하는 것이 아니라 HBM 왕복 횟수를 줄이는 것임.

- 기존(CUTLASS): FC1 결과를 BF16으로 HBM에 쓴 뒤 다시 읽어 SwiGLU와 FP4 양자화를 수행함.
- 개선(TensorRT-LLM Gen NVFP4 MoE): FC1 안에서 Gather + SwiGLU + FP4 출력을 한 커널로 융합해 중간 결과를 HBM에 쓰지 않음.

### KV-aware 라우팅

| 지표 (16 GPU) | Round-robin | KV-aware |
|---|---|---|
| 프롬프트 토큰 KV 캐시 히트율 | 64% | 70% |
| 후속 요청 텍스트 토큰 히트율 | 41% | 64% |
| SLO 내 처리량 | 14.63 req/s | 16.03 req/s (+9.6%) |

GPU 간 부하 균형도 거의 유지됨(1.001 → 1.026, 1.0이 완벽한 균형).

## 정리

- 모델 품질은 데이터, 학습 파이프라인, 평가 체계를 얼마나 갖췄는지에 달려 있음.
- 비전처럼 새 모달리티를 붙이면 학습 안정성 문제가 생기므로, 재현과 이분 탐색 같은 디버깅 역량이 필요함.
- 디코드 단계의 MoE는 연산이 아니라 메모리 이동이 병목이므로, 커널 융합으로 HBM 접근을 줄이는 것이 핵심임.
- 서빙에서는 KV 캐시 재사용을 고려한 라우팅이 처리량을 높임.
